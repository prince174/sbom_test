# Dependency-Track: как получить пути к уязвимому компоненту через API

Этот гайд описывает алгоритм, как по уязвимости определить какой компонент в виде прямой зависимости нужно обновить и как подготовить тело для задачи Jira.

Пример: обнаружен `@babel/traverse@7.23.0` с `GHSA-67hx-6x53-jw92` — алиасом `CVE-2023-45133`.
Заранее мы **не знаем**, что компонент приходит через `@babel/core`: это нужно выяснить обходом графа.

## Что необходимо

- UUID проекта в Dependency-Track.
- Загруженный и обработанный SBOM с зависимостями, а не только списком компонентов.
- Завершённый анализ уязвимостей и работающий источник advisory.
- Авторизация для чтения находок и графа проекта.

## Алгоритм

Обозначения `core-uuid`, `traverse-uuid` и другие ниже — условные имена настоящих UUID.
JSON-примеры сокращены. Дополнительные ветви `react` и `lodash` используются только для объяснения алгоритма, они не являются результатом нашего теста.

## Шаг 1. Получить находки проекта и определить цель поиска

```http
GET /api/v1/finding/project/{projectUuid}
```

Из списка выбираем нужную находку:

```json
[
  {
    "component": {
      "uuid": "traverse-uuid",
      "group": "@babel",
      "name": "traverse",
      "version": "7.23.0"
    },
    "vulnerability": {
      "vulnId": "GHSA-67hx-6x53-jw92"
    }
  }
]
```

Запоминаем `component.uuid`:

```text
targetUuid = traverse-uuid
```

Это конечная точка искомых путей.
Не выбираем родителя по названию пакета или по предположению.
Если находки относятся к нескольким UUID компонентов, каждый из них нужно обработать отдельно.

## Шаг 2. Получить все прямые зависимости проекта

```http
GET /api/v1/dependencyGraph/project/{projectUuid}/directDependencies
```

Допустим, ответ содержит:

```json
[
  { "uuid": "core-uuid", "name": "core", "version": "7.23.0" },
  { "uuid": "react-uuid", "name": "react" },
  { "uuid": "lodash-uuid", "name": "lodash" }
]
```

Сохраняем все связи:

```text
projectUuid → core-uuid
projectUuid → react-uuid
projectUuid → lodash-uuid
```

Все три компонента помещаем в очередь обхода. Пока неизвестно, какая ветвь приведёт к `traverse`.

## Шаг 3. Запросить зависимости каждого обнаруженного компонента

Для первого компонента в очереди:

```http
GET /api/v1/dependencyGraph/component/{coreUuid}/directDependencies
```

Пример ответа:

```json
[
  { "uuid": "parser-uuid", "name": "parser" },
  { "uuid": "traverse-uuid", "name": "traverse" },
  { "uuid": "helper-uuid", "name": "helper-module-transforms" }
]
```

Сохраняем рёбра:

```text
core-uuid → parser-uuid
core-uuid → traverse-uuid
core-uuid → helper-uuid
```

UUID второго компонента совпал с целью из шага 1. Теперь подтверждён первый путь:

```text
Приложение → @babel/core → @babel/traverse
```

Именно из ответа этого запроса мы узнали, что `core` зависит от нужного `traverse`. `core` — результат поиска, а не входное условие.

## Шаг 4. Обойти остальные ветви

Продолжаем запрашивать зависимости остальных компонентов:

```http
GET /api/v1/dependencyGraph/component/{очереднойUuid}/directDependencies
```

Например, ответ для `helper-module-transforms` содержит тот же `traverse-uuid`. Значит, существует ещё один путь:

```text
Приложение → @babel/core → @babel/helper-module-transforms → @babel/traverse
```

Правила обхода:

- Каждый узел запрашиваем один раз по UUID.
- Сохраняем каждую связь, даже если дочерний узел уже встречался у другого родителя.
- Не останавливаемся на первом совпадении: другая прямая зависимость тоже может приводить уязвимый компонент.
- Ошибка API не считается пустым списком зависимостей. При незавершённом обходе результат помечаем как неполный.

## Шаг 5. Найти пути в сохранённом графе

После обхода имеем две структуры:

```text
nodes: UUID → название, версия, PURL
edges: UUID родителя → список UUID зависимостей
```

Теперь наш код ищет пути от `projectUuid` до `targetUuid`. Это вычисление на стороне интеграции, а не отдельный ответ API Dependency-Track.

Упрощённый Python-псевдокод, где `get_json()` выполняет авторизованный GET и проверяет ошибки:

```python
from collections import deque

nodes = {}
edges = {}
visited = set()
queue = deque([("project", project_uuid)])

while queue:
    kind, uid = queue.popleft()
    if uid in visited:
        continue

    children = get_json(
        f"/api/v1/dependencyGraph/{kind}/{uid}/directDependencies"
    )
    visited.add(uid)
    edges[uid] = [child["uuid"] for child in children]

    for child in children:
        child_uuid = child["uuid"]
        nodes[child_uuid] = child
        queue.append(("component", child_uuid))

paths = []

def find_paths(uid, path):
    if uid == target_uuid:
        paths.append(path)
        return

    for child_uuid in edges.get(uid, []):
        if child_uuid not in path:
            find_paths(child_uuid, path + [child_uuid])

find_paths(project_uuid, [project_uuid])
```

Этот пример рассчитан на граф пакетов нашего стенда. Если SBOM содержит сервисы, их нужно обрабатывать отдельно с учётом возможностей API используемой версии, а не автоматически направлять их UUID в endpoint компонентов.

`visited` предотвращает повторные запросы API. Проверка `child_uuid not in path` предотвращает циклы при поиске путей. Это разные проверки: глобальный запрет повторных узлов на этапе поиска путей мог бы скрыть альтернативные пути.

Для больших графов число путей может быть очень велико. Если интеграция ограничивает глубину или число путей, это ограничение нужно явно отражать в результате. Если требуются только прямые зависимости, приводящие компонент, можно вычислять достижимость без перечисления всех путей.

## Шаг 6. Определить прямые зависимости для задачи

В каждом пути берём первый компонент после проекта:

| Путь | Прямая зависимость |
|---|---|
| Приложение → core → traverse | core |
| Приложение → core → helper → traverse | core |
| Приложение → другой пакет → traverse | другой пакет |

Удаляем повторы по UUID. В нашем реальном тесте все три пути начинаются с `@babel/core@7.23.0`.

На основании графа можно сформировать утверждение:

> Уязвимый `@babel/traverse@7.23.0` поступает в проект через прямую зависимость `@babel/core@7.23.0`. Пути подтверждены ответами API графа зависимостей.

Если уязвимый компонент сам является прямой зависимостью, путь будет состоять из проекта и этого компонента. Искать дополнительного родителя в таком случае не требуется.

## Шаг 7. Отдельно получить рекомендацию по исправлению

Граф подтверждает **существующую цепочку**, но не вычисляет исправленную версию родителя.

В проверенном примере поле `vulnerability.description` из находки содержит текст advisory с рекомендацией `@babel/core >= 7.23.2`. Поэтому здесь рекомендацию можно извлечь из ответа Dependency-Track.

Это не универсальное структурированное поле `parentFixVersion`. Для другой CVE такой рекомендации может не быть. Тогда нужны advisory разработчиков, метаданные зависимостей новых версий и проверка обновления в проекте.

Поле `latestVersion` также нельзя автоматически считать минимальной исправленной или совместимой версией.

На стенде в исходном `package.json` был тестовый override, закрепляющий `traverse@7.23.0`. Его пришлось удалить. Этот факт получен из файлов проекта, а не из графа Dependency-Track.

Для Jira нужно разделять:

| Данные | Источник |
|---|---|
| Уязвимый компонент и advisory | API находок |
| Пути и прямые зависимости | API графа + обход в интеграции |
| Рекомендованная версия родителя | Текст advisory или отдельный анализ обновления |
| Overrides и другие ограничения установки | Файлы проекта |
| Подтверждение устранения | Новый состав, SBOM и повторный анализ |

## Что фактически получилось на стенде

Получены три пути к одному UUID уязвимого компонента:

```text
Приложение → @babel/core → @babel/traverse

Приложение → @babel/core → @babel/helper-module-transforms
           → @babel/traverse

Приложение → @babel/core → @babel/helper-module-transforms
           → @babel/helper-module-imports → @babel/traverse
```

После удаления тестового override и обновления `core` с `7.23.0` до `7.23.2` менеджер npm разрешил `traverse@7.29.8`. Новый SBOM был загружен отдельной версией проекта; целевая находка исчезла. Другая уязвимость `core` осталась: исторический минимум для одной CVE не означает отсутствие всех уязвимостей.

## Ограничения достоверности

«Подтверждённый путь» означает, что каждое ребро получено из API и конечный UUID совпал с UUID компонента из находки. Это подтверждение импортированного графа, а не независимая проверка состава файлов или исполнимости уязвимого кода.

Если в SBOM отсутствуют связи или корень графа, нахождение компонента в списке не гарантирует возможность восстановить путь. Корректный результат в такой ситуации:

> Источник транзитивной зависимости не установлен по имеющемуся графу.

Отсутствие пути не означает отсутствие компонента или уязвимости. При изменении SBOM во время обхода ответы могут относиться к разным состояниям проекта; для автоматизации следует использовать стабильную версию проекта и фиксировать время получения данных.
